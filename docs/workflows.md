## Content states and publication

The tenant administrator writes and publishes. The only logical content states are **Draft** and **Published**:

| Condition / action | Result |
| --- | --- |
| No active public pointer | Draft, including after unpublish; historical snapshots may remain |
| Active public pointer | Published; a pending draft version may coexist |
| Save new content or changes to a live item | Create/update an editable draft version; leave the current publication untouched |
| Explicit publish by the tenant administrator | Validate tenant/reference/media eligibility and expected versions; atomically create the immutable publication snapshot and move the active pointer; logical state Published |
| Unpublish or revoke public eligibility | Remove the active public pointer/eligibility, block controlled delivery and invalidate affected outputs; logical state Draft |
| Restore a historical snapshot | Create a draft version; the administrator must explicitly publish it; restoration never changes live output automatically |

No mandatory clinical classification, Reviewed state, reviewer approval records, self-review constraint, review-invalidation requirement or additional Archived workflow is introduced. Describing medical subjects does not create a separate editor/reviewer/publisher permission model. Recorded permission to publish patient-derived cases/testimonials remains a distinct eligibility requirement.

Use optimistic expected-version checks for saves and publication. A stale write/publish must reject the conflict rather than overwrite another administrator. Preview renders only authorized drafts with no public cache/indexing. Ordinary unpublish/revoke uses the administrator's own authority; no review wait or automatic republish follows it.

Brand/menu/theme changes also save Draft and reach live only through explicit Publish, preserving configuration/reference versions and optimistic conflicts. The MVP uses two original themes with a shared-schema section catalog and limited color/font/layout, no arbitrary HTML/scripts. S03-D01 approves the minimum introduction/rich-text layout only; full themes/section catalog remains S13. Full Web Builder remains future direction, not a new content state, review gate or MVP delivery claim.

## Approved retention and deadlines

| Data | Required deadline |
| --- | --- |
| Closed lead, including contact and notes | Delete at the earlier of **closure + 90 days** and **last substantive human contact/activity + 180 days** |
| Other lead | Delete after **180 days of inactivity** |
| Spam | Retain for **30 days**, subject to an already earlier deadline |
| Redacted audit | Retain for **365 days**; do not retain contact/message content as audit payload |

Measure inactivity from the last substantive human contact/activity, using creation only when none exists. Real substantive activity updates that reference and the normal inactivity deadline. Views, polling, notification/job retries, synthetic timestamp touches or assignment/status toggles alone do not count. A still-open lead's normal deadline is that reference + 180 days. For a closed lead, use the earlier of closure + 90 days and that reference + 180 days. There is no immutable lifetime cap calculated from creation. An explicit extension beyond the applicable normal policy deadline requires an authorized tenant administrator, a recorded reason and expiry. The storage/calculation representation remains an implementation detail; no separate expiry ledger is required.

Documentation example only: created day 0, substantive human contact day 150, still open → inactivity deadline day 330. A view on day 170 does not move that deadline. If closed on day 160 → the earlier deadline is day 250, not day 330. This example is not an application fixture or runtime test.

Notify tenant administrators **7 days before deletion**; if a new shorter deadline leaves less notice, notify promptly without postponing expiry. At expiry enforce deletion and prevent expired records from continuing to appear; failures remain visible and do not authorize an extension. Deadline/extension checks must cover direct reads and background deletion, including concurrent reopen/extension/deletion attempts.

Retain deletion/revocation evidence sufficient to prevent restored data becoming eligible again, with minimal redacted identifiers. Tenant-wide deletion and backup retention/expiry are unresolved D5 policies; the approved lead/audit deadlines do not select a backup schedule or tenant lifecycle. Resolve backup semantics before live use and reapply current deletion/retention/revocation decisions before exposing restored data. None of these periods is claimed to be a clinical or legal retention law.

## Media publication permission and withdrawal

Original uploads stay private/quarantined. MVP accepts **JPEG, PNG and WebP**, at most **5 MiB per image**; reject SVG and remote URL imports. This cap is accepted, not merely proposed. Validate type/content/size, process safely and remove unnecessary metadata. Pixel/decompression bounds, safe decoding/transforms and exact library/provider remain technical contracts, not selected implementations. Patient-derived case/gallery/testimonial material needs recorded permission-to-publish evidence and scope before public eligibility. This is not a clinical Reviewed gate. Permission withdrawal applies to all affected published references and derivatives, including historical snapshots still reachable through controlled routes.

- Private originals require current authorization before signed access; signed URLs last at most **60 seconds**. Never expose a permanent publicly readable original bucket URL.
- Public derivatives use a route controlled by **current eligibility**. A snapshot reference or previously queued job cannot grant public access on its own.
- Withdrawal blocks eligibility **immediately**. Controlled delivery must stop within the accepted future target **≤60 seconds**, including outstanding access/cache paths under platform control.
- Cache purge is asynchronous with target **≤5 minutes** and explicit **pending / failed / retry** handling. These are delivery-operation statuses, not content states. Report eligibility blocking separately from pending purge; do not claim cleanup succeeded when it failed.
- Stale retries must recheck current eligibility and cannot regrant permission or recreate public delivery. Failures are visible and bounded retries preserve denial.
- These targets are accepted future acceptance values, not measured SLA results. No promise covers copies already downloaded or retained by third parties.
